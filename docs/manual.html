1. 全体像

80×45 タイルのトーラス（端がつながった）盤面で、草・草食獣・肉食獣・死骸・土壌養分の5つが相互作用するリアルタイムシミュレーション。プレイヤーの介入（神のダイヤル・賭け）はまだ無く、今は「生態系が放っておくとどう振る舞うか」を観察する段階。

時間

1 tick = 2000ms。5 tick = 1 エポック（10秒、実時間は変わらない）。エポックは現状カウンタだけで、何も起きない（将来の賭け精算・気候抽選のフック）。

盤面

80×45 = 3,600 タイル。1タイル 16px。上下左右が折り返してつながる。

初期状態

草はほぼ全面に生えた状態から始まり、草食獣150・肉食獣12がランダム配置。乱数シードは起動時刻（UIからの指定は不可）。

典型的な推移

草食獣が爆発的に増える → 草を食べ尽くす／捕食者が増えすぎる → 崩壊 → 生き残りと土壌から回復、の波。絶滅は普通に起きる。

2. 因果ループ（モデルの本体）

ストック（箱）とフロー（矢印）。機能追加を考えるときは、まず「どの箱を増やすか／どの矢印を足す・変えるか」をこの図の上で言えるようにする。

このループの性質

  • 草は無から生えない。成長は必ず同じタイルの土壌養分を1:1で消費する。養分がゼロなら何も起きない。
  • 養分の入口は4つ：枯死（自タイルへ）・散布（隣8タイルへ）・排泄・死骸の分解。前の2つは動物がいなくても働く（遅い）、後の2つは動物由来（速い）。
  • 遅延は死骸の分解だけ。死んでから養分になるまで10 tick。design.md が想定する「草食獣→捕食者の遅延」はまだ無い（捕食の効果は即時）。
  • 質量は保存されない。散布は元のタイルのbiomassを減らさずに養分を生む。死骸はその個体が何を食べたかに関係なく一定量（0.4）を返す。モデルは定性的な因果の再現を目的にしていて、物質収支は合わせていない。

3. 1 tick の処理順

順番に意味がある。後の段は前の段の結果を見て動く。すべて Worker 内の sim/loop.ts の tick() で実行される。

  1. 草 stepGrass
    1. 全タイルのbiomassをスナップショット（走査順で結果が偏らないように）
    2. biomass > 0 のタイルごとに：自分のbiomassの senescenceRate 分を減らして自タイルの養分に足す（枯死）。さらに spreadRate 分を8等分して隣の養分に足す（散布、元は減らない）
    3. 全タイルで成長：余地 = growthRate × (capacity − biomass)、成長量 = min(余地, 養分)。養分を同量減らす
  2. 草食獣 stepHerbivores（配列順に1体ずつ。前の個体が食べた結果を次の個体が見る）
  3. 肉食獣 stepCarnivores（草食獣が動き終わった後の位置を狙う。この段で食べられた草食獣は段の最後にまとめて除去）
  4. 死骸 stepCarcasses（全死骸が養分を放出し、10 tick 経ったものを消す）
  5. 描画差分の計算 deriveHeightAndColor（見た目の段階が変わったタイルだけを返す）
  6. エポックの判定（5 tickごとにカウンタを進めるだけ）

死骸による通行止めは、各段の開始時点に存在する死骸で判定する。草食獣の段で出た死骸は、同じtickの肉食獣の段では通行止めになる。

4.3 草食獣 ●

状態は 空腹度 hunger（0=満腹〜1=餓死）と年齢 ageの2つだけ。この2つは独立していて、どちらか一方で死ぬ。蓄えという概念は無く、空腹度は毎tick必ず上がり、食べた時だけ下がる。個体には誕生時に振られる安定id（id）もあるが、これは表示側（移動の補間・向きの判定、5章）が個体を追跡するためだけの情報で、シミュレーションのロジックからは参照されない。

  1. 休憩判定：直前に採食して rest（残り休憩tick数）が1以上残っていれば、それを1減らして今回の移動・空腹・採食（下記2〜4）を丸ごとスキップする（その場に留まり、空腹度も変化しない）。加齢・死・繁殖の判定（5〜7）はこの間も通常通り行う
  2. 移動：（休憩中でなければ）自タイルと隣8タイルのうち、草が一番多いタイルへ1マス動く（死骸のあるタイルは候補から外す。同じ量のときはわずかな乱数で決まり、その場に留まるより隣へ移りやすい）
  3. 空腹：hunger += 0.05
  4. 採食：そのタイルの草が 0.1 を超えていれば最大 0.15 食べ、hunger −= 0.1 × (食べた量 / 0.15)。食べた量の半分をそのタイルの養分に返す（排泄）。実際に一口でも食べたら rest = HERBIVORE_PARAMS.restTicksAfterEating（2）をセットし、次の2tickは休憩に入る
  5. 加齢：age += 1
  6. 死：hunger ≥ 1（餓死）または age > 200（老衰）でその場に死骸を残して消える
  7. 繁殖：生き残り、かつ hunger ≤ 0.15 なら同じタイルに子を1体（子の空腹度 0.5）。親は hunger += 0.3。無性生殖

収支の目安：食べるたびに restTicksAfterEating（2）tick休憩が挟まるため、最速でも「採食tickで −0.05、休憩tick×2で±0」の3tick周期。餓死しない限り食べ続けられれば空腹度は3tickあたり0.05ずつ下がる（休憩が無かった頃は1tickあたり0.05だったので、tick数でいうと1/3の速さ）。食べられる頻度がこれより低いと横ばい〜餓死に向かう。飢えだけで死ぬまで最短 20 tick（約40秒、約4エポック、休憩の有無に関係ない — 休憩中は空腹度が上がらないため）。

4.4 肉食獣 ▲

草食獣と同じ2つの状態（空腹度・年齢）＋同じ表示専用の安定id。違いは餌が「草」ではなく「そのタイルにいる草食獣」であること。

  1. 休憩判定：草食獣と同じ仕組み。直前の捕食で rest が残っていれば1減らして移動・空腹・捕食（下記2〜4）をスキップする
  2. 移動：（休憩中でなければ）自タイルと隣8タイルのうち、まだ誰にも捕まっていない草食獣が一番多いタイルへ1マス動く（死骸タイルは除外）
  3. 空腹：hunger += 0.04
  4. 捕食：そのタイルに草食獣がいれば1体捕まえて hunger −= 0.3。捕まった草食獣はこのtickの終わりに消え、死骸は残さない（養分は捕食者に移る扱い）。1体の獲物を2体の捕食者が取り合うことは無い。捕食に成功したら rest = CARNIVORE_PARAMS.restTicksAfterEating（1）をセット
  5. 加齢：age += 1
  6. 死：hunger ≥ 1 または age > 600 でその場に死骸を残して消える
  7. 繁殖：hunger ≤ 0.05 なら子を1体（子の空腹度 0.5）。親は hunger += 0.7

収支の目安：1回の捕食（−0.3）で約7 tick分の空腹を賄う。捕食の直後は1tick休むが、空腹度は上がらないので収支には影響しない（草食獣と違い、捕食のリリーフ量が空腹の増加量よりずっと大きいため、休憩を挟んでも大きく下振れする傾向自体は変わらない）。繁殖するには捕食を何度も重ねて空腹度を 0.05 以下まで下げる必要がある。

1タイルに描くのは1枚のスプライト。design.md の優先順位（動物 > 植物 > 背景）に従って下から重ねる。草・草食獣・肉食獣とも、[高さ/空腹バケット] × [色バケット/フレーム] のベクタ図形をあらかじめ焼き込んだシートから blit する（render/sprites.ts）。

現状のずれ：design.md は「背景色=量、草の形=構造」を独立した2軸にしたいが、今は両方とも biomass の1変数から決まっていて独立していない。土壌養分（fertility）は画面に出ない。

部分描画：毎tick塗り直すのは「見た目の段階が変わった草タイル」＋「前tickか今tickに動物・死骸がいたタイル」だけ。HUDの dirty がその数。

移動の補間：動物の位置は tick の瞬間に新しいタイルへ飛ぶのではなく、前 tick の位置から今 tick の位置まで tick 時間（2000ms）いっぱいかけて滑らかに動く（render/renderer.ts の from/to 補間）。捕食・採食の瞬間をジャンプカットにせず、目で追える「シーン」にするための変更。死骸は発生後は動かないので基本はそのままだが、発生した最初の1tick（age === 0）だけは例外：移動は死亡判定より先に起きる（3章）ため、死んだ個体は死亡tickのうちに最大1タイル動いてから死ぬことがあり、死骸は「動物が最後に生きて描かれた位置」から1タイルずれて発生しうる。これも他の動物と同様、その1tickだけ CarcassSnapshot.fromX/fromY（死ぬ前、移動前の位置）から発生位置まで補間で滑らせる（render/renderer.ts の carcassGlideFrom）。2tick目以降（age ≥ 1）は完全に静止（10章）。採食・捕食した直後の休憩tick（4.3/4.4の restTicksAfterEating）は前後の位置が同じなので、この補間は自然にゼロ距離になり、その個体だけその場に留まって見える。ただし静止だけでは「食べている」ことまでは伝わらなかった（口パクアニメーションが常時ループしていて、休憩中かどうかに関わらず同じに見えていたため。10章）。前tick→今tickの対応は配列の同じ添字同士ではなく、個体の安定id（HerbivoreState.id / CarnivoreState.id、4.3/4.4章）で引き当てる。死亡はswap-remove（末尾の個体を空いた枠に詰める）で実装されているため、添字同士の対応だと「今tick死んだ個体の枠に、盤面の別の場所にいた無関係な個体が来た」ケースを同一個体の移動と誤認し、その個体が盤面を斜めに横切って飛ぶように見えるバグがあった（10章）。

アニメーションのループ切り替え：各種のベイク済み8フレームは「歩き」（フレーム0〜4、口はほぼ閉じたまま）と「採食/捕食」（フレーム5〜7、口を大きく開閉する一噛み）の2ループに分かれている（render/sprites.ts の pickAnimalFrame）。どちらを再生するかはrest（HerbivoreState.rest / CarnivoreState.rest）が種ごとの restTicksAfterEating（4.3/4.4章の休憩tick数）と一致するかどうかで決まる（render/renderer.ts の computeGlide が返す eating）。一致する＝噛んだ直後の最初の1tickだけ採食/捕食ループを再生し、休憩がそれより長く続く場合の残りのtickは（その場で止まってはいるが）歩きループにフォールバックする。どのtickのrestを見るかは種によって違う（computeGlide の delayedEating 引数）：

  • 草食獣（1tickずらす）：移動と採食は同じ1tickの中で起きる（3章）ので、噛んだ瞬間のtickのスナップショットは rest>0 でありながら、その個体はまだ「噛んだ先のタイルへ歩いている」最中（前tick位置→今tickの着地位置へ滑っている途中）。1個体前（この個体が最後に rest を報告したときの値）を見ることで、実際にその場で静止して消化している次のtickの窓に噛みモーションが乗るようにしている。この補正を入れる前は、歩いている最中に口が開き、実際に止まって消化しているtickでは口が閉じるという、順序が逆のバグがあった（10章）。草食獣本体は消えないので、この「1tick遅らせて見せる」が成立する。
  • 肉食獣（ずらさない、今tickのrestをそのまま見る）：捕食は獲物をそのtickのうちにデータごと消してしまう（後述の被食シーン参照）ので、草食獣と同じ理屈は成立しない——「次のtick、静止してから見せる」ための獲物がもう存在しない。捕食が成立したそのtick（＝捕食者がまだその獲物のいた場所へ歩いている最中のtick）で噛みモーションを出し、被食シーン（後述）と時間を合わせる。旧実装ではここも1tickずらしていたため、獲物が消えてから1tick丸ごと何も起きず、次のtickで唐突にゴーストが湧いて縮む、という順序のおかしさがあった（ユーザー報告、10章）。

草の見た目の遅延コミット：1 tick分の草の変化（DirtyTile[]）は、そのtickが届いた瞬間には反映しない。前 tick の位置から今 tick の位置への補間（上記）が完了する（progress=1に達する）まで RendererState.pendingDirty として保留し、動物が実際にそのタイルへ到着した瞬間にだけ colorBucket/heightCat へ反映して塗り直す（render/renderer.ts の commitPendingDirty）。以前は tick が届いた瞬間に即座に反映していたため、草食獣がそのタイルへ歩いて到着する前に草がすでに減っている（減った後に乗ってくるように見える）という順序のおかしさがあった。この遅延により、見た目の順序は「移動 → （到着して）食べる → 草が減る」になる。一時停止中もこの補間ループ自体は止まらないため（表示の仕様冒頭）、コミットは次のtickの到着を待たずに progress=1 の時点で必ず起きる。

被食シーン（捕食された獲物が消えていく演出）：捕食された草食獣は、捕まったそのtickのうちに配列から取り除かれ（4.4章）、死骸も残さない（捕食された個体は死骸を残さない、2章）——つまりシム側のデータには「食べられた」という事実そのものを表す実体が一切残らない。そこで stepCarnivores（sim/carnivore.ts）は、捕食が成立した瞬間の座標（＝捕食者自身の移動先タイル。捕食は必ず捕食者が移動した先のタイルで成立する）を PredationEvent として別途収集し、tickのメッセージに predations（PredationSnapshot、id・種別を持たない座標だけの1tick限りのリスト）として毎tick乗せる（sim/loop.ts の TickResult.predations → worker/sim.worker.ts）。レンダラーは、捕食が成立したそのtick自体（進行方向の補間 progress=0〜1）にわたって、その座標に汎用の草食獣シルエットを縮小・フェードアウトさせながら描く（render/renderer.ts の drawPredations/drawPredation）。捕食者本体より後（上）に描くため、重なる部分はクリップではなくアルファ合成になる。捕食者は tick の最初（progress=0）はまだその座標から離れた場所を歩いている途中で、被食シーンの方は満alpha・満スケールでそこに存在しており、捕食者が近づくにつれて（progress→1）薄く・小さくなっていく——両者が同時にほぼ不透明・同じ場所になる瞬間はほとんど無いため、旧実装（後述）が抱えていたクリップ問題も設計上ほぼ起きない。座標は固定（動かない）ので塗り直し対象タイルの判定（overlayTileSet）も単純：predations にある座標をそのままその tick の対象に足すだけ（addPredationTiles）。次tickには predations が新しいリスト（この tick に成立した捕食だけ）に入れ替わるので、古い座標は自然に対象から外れ、直前tickの最終フレームとの和集合により最後の1回だけ確実に塗り直されて消える——死骸の fromX/fromY（4.5章）と同じ「1tick限りの補間」の考え方を、獲物という実体の無いイベントに適用したもの。

以前の実装（判断の記録に経緯あり、10章）は、捕食者の eating（上記、当時は肉食獣も1tickずらしていた）を根拠に、捕食者自身の位置の近くへ汎用シルエットを重ねて描く「ゴースト」演出だった。これは3つの意味でおかしかった：(1) 獲物が消えるのは捕食tick（移動の最中）なのに、ゴーストが出るのはその次のtick（静止後）——1tickの空白ができ、「消える→何も起きない→急に別の何かが湧いて縮む」という順に見えていた。(2) ゴーストを捕食者と同じ中心・同じくらいの大きさで描いていたため、捕食者本体の不透明なスプライトに隠れて実質見えなかった。捕食者から少しずらし、描画順を後にすることで一時的に緩和したが、これは対症療法で、そもそも「捕食者に対する演出」として設計していたこと自体が筋違いだった（ユーザー指摘：「普通こういうのって状態遷移だと思う」）。(3) ゴーストがはみ出す先のタイルを塗り直し対象の判定が把握しておらず、消えたはずの最終フレームが数tick居座るバグもあった。今の設計は、被食を捕食者の付属演出ではなく独立したイベント（座標と寿命1tickだけを持つ）として扱うことで、この3つを同時に解消している。

デバッグ用ダッシュボード（ヒストグラム）：盤面キャンバスの下に、草食獣・草の分布を毎tick描き直す3枚の小さな棒グラフ（#hist-grass/#hist-hunger/#hist-age、render/dashboard.ts）がある。design.md/上記の「表示の仕様」が指すゲームとしての見た目とは別枠の、パラメータ調整のための観測用ツール——不変条件にもピラミッドの原則にも関与しない。中身は「草のbiomassをタイル単位で20分割ビン集計」「草食獣のhunger/ageを個体単位で20分割ビン集計」の3つで、ビン集計そのもの（sim/stats.ts の computeHistogram/histogramMean）は他の草・動物のロジックと同じく単体テストがある一方、キャンバス描画（drawHistogram）は他の描画コードと同様に実機目視のみ（7章の注記に同じ理由：DOM無しのテスト環境では検証できない）。

9. 既知の単純化・技術的負債

  • 処理順の偏り：個体は配列順に1体ずつ処理され、前の個体の結果を後の個体が見る。配列の前の方の個体がやや有利。
  • 草食獣は逃げない。捕食者の位置を見ずに草だけを追う。捕食は隣接すれば必ず成功する。
  • 視野は隣1マスだけ。HERBIVORE_PARAMS.visionRadius は定義されているが使われていない。
  • 無性生殖。検討の上、現段階では雌雄を入れないと判断（10章）。
  • 質量非保存（2章）。散布と死骸が、実質的な外部からの養分流入になっている。
  • 長時間の検証手段が無い。回復のような数千tickの挙動は、DEFAULT_TICK_MS を一時的に 20 に書き換えて早送りして確認している。倍速UIか、ヘッドレスで回す検証スクリプトがあると良い。
  • 乱数シードを固定できない。同じ条件の再現・比較ができない。
  • 1回の観察に依存した調整がある。実機確認の多くは1回の試行。シードによって結果が変わりうる。

判断理由・経緯
草のbiomassと草食獣のhunger/ageをビン集計するデバッグ用ダッシュボード（ヒストグラム3枚）を追加（sim/stats.ts の computeHistogram/histogramMean、render/dashboard.ts、WorkerToMainへのhistogramsフィールド追加）ユーザー指示：「草や草食動物のダッシュボード化ヒストグラムが欲しい。あなたもその数値を確認してパラメータ調整に使って」。集計はワーカー側（全タイル・全個体の生データを持っている場所）で行い、メインスレッドには20ビン×3の集計済み配列だけを送る——生の3,600タイル分biomassや個体ごとのhunger/ageをそのまま毎tick送る案は、既存のスナップショット（4.3/4.4章のid/rest等、表示に要る最小限だけを送る設計）と方針が逆行するため採らなかった。ビン集計・平均の計算自体は草食獣・肉食獣どちらの種も知らない汎用関数にしてsim/stats.tsに置き、モジュール境界（6章）を保った。

噛みアニメーションの再生条件を「1tickずらしたrestが0より大きいか」から「1tickずらしたrestが種ごとのrestTicksAfterEatingと一致するか」に変更（休憇が複数tickに伸びても最初の1tickだけ噛む）ユーザー報告：「草食動物はずっと食べてる感じがする」。まず1 tickの処理順自体（移動→全体の移動待ち→イベント実行→反映、に分け直す案）を検討したが、既知の処理順バイアス（9章）は解消できても「ずっと食べてる」の実体（後述）には効かないと判断し保留。次に grazeBiomassThreshold（採食可能な草の量の下限）を上げる案を実際にシミュレーションで検証（80×45盤・400tick・固定シード）：0.1→0.6まで6倍に上げても、画面上で咀嚼モーションを表示している個体の割合は41%→34%としか下がらなかった（閾値を厳しくすると群れの平衡個体数が自動的に下がり、生存者1体あたりの採食機会はあまり変わらないため）。副作用（最大個体数・肉食獣の生存バランス）の方が大きく、見送り。次に「空腹度が一定以上のときだけ採食を試みる」ゲート（eatHungerThreshold）を実装して検証したところ、効果なしか群れ全滅のどちらかにしかならないことが判明：ゲート値を繁殖しきい値（0.15）以下にすると常にほぼ成立してしまい無意味、0.15を超えると「食べて少し満たされる→ゲート値未満になり停止→空腹度上昇→ゲート値到達でまた食べる」が0.15を跨がない周期に固定され、二度と繁殖できなくなる（実際に0.25で試したところ、初期150体が一度も繁殖できないままtick200＝寿命ちょうどで一斉に老衰死した）。空腹度の上昇幅(0.05)と一口の回復量(0.1)がちょうど2:1という現在の数値設計のせいで中間の値が存在しないため、この案は不採用としコードを元に戻した。最後に、そもそも休憩tickを増やして採食の頻度自体を下げる案（restTicksAfterEatingを1から増やす）を試したところ、逆効果だと分かった：休憇中は常に「1tickずらしたrest>0」が真になるため、休憩を伸ばすほど画面上は「噛んでいる時間」が増えてしまう（同条件のシミュレーションで、rest=1→5で咀嚼表示の個体割合が41%→76%まで上昇）。これはrestTicksAfterEatingを安全に増やすための前提条件として、噛みモーションの表示条件そのものにあったバグ（休憩＝常に噛んでいる、という誤った対応）を先に直す必要があることを意味する。今回のコミットではその表示条件のバグだけを修正した（数値パラメータには触れていない）。restTicksAfterEatingは両種とも現在1のままなので、この修正自体は見た目に変化を生まない（rest∈{0,1}の範囲では新旧の判定は常に一致する）。「ずっと食べてる」感を実際に減らすには、この修正を前提にrestTicksAfterEatingを上げる調整が次の一手になるが、それ自体は生態系バランス（個体数の均衡・INV-11/13）に実質的な影響を与えうることを検証済みなので、実施する場合は改めて数値を検証してから合意する
草の見た目の変化を動物の到着まで遅延コミットし、噛みアニメーションの再生タイミングを1tickずらし、捕食された獲物に縮小フェードの「食べられていく」演出を追加ユーザー報告：「草食動物が食べる草の上に来る前に草が減る→乗って食べる、のように見える」「移動⇒食べる⇒草が減る の順にしてほしい」「肉食は隣接⇒食べるモーション⇒食べられていく、のはず」。原因は2つ複合していた。(1) tickの草の差分（DirtyTile[]）はtick到着と同時に即座にcolorBucketへ反映・塗り直ししていたが、その個体の見た目上の移動（前tick位置→今tick位置への補間）はそこから tickDurationMs かけて進む。つまり草は着地の瞬間に減り、動物はそこへ2秒近くかけて歩いていく——原因と結果が逆順に見えていた。(2) 噛みアニメーション（前回の判断のrest>0判定）も、移動と採食が同じtickの中で起きるという仕様（3章）のせいで、噛んだ瞬間のtickではまだ歩いている最中なのに口が開き、実際にその場で静止して消化する次のtickではrestがすでに0に減っていて口が閉じる、という順序違いがあった。捕食された獲物についても、捕まった瞬間のtickで配列から即消えるため、捕食者がまだそのタイルへ歩いている最中に獲物が瞬時に消えて見えていた。修正は3点：草の差分をRendererState.pendingDirtyとして保留し、その個体の補間がprogress=1に達した瞬間（=到着した瞬間）にだけ反映する（commitPendingDirty）／噛みアニメーションの判定を「今tickのrest」から「1tick前に報告されたrest」に変更し、computeGlideの返り値にeatingを追加（各個体の前回restをGlideEntry.restとして引き継ぐ）／捕食者がeatingである間、その足元に汎用の草食獣シルエットを縮小・フェードアウトで重ねて描くdrawPreyGhostを追加（実際に食べられた個体の見た目・idは使わない。捕食成立時点で送信データにはもう残っていないため）。computeGlideの単体テストに1tickずらしの検証を追加。草の遅延コミットとghost演出自体はキャンバス描画で単体テスト環境（DOM無し）では検証できないため、実機観察のみ（7章はテスト化を検討）
死骸の描画から90°回転（「横倒し」演出）を削除し、生体と同じ向きのまま描くように変更ユーザー報告：「死体になると縦になる感じがして急に動くのに違和感がある」。4×4の小さい盤面でユーザー指示のもと実機確認したところ、特に肉食獣の死骸（生体の横幅 bw が縦幅 bh よりかなり大きい：0.88 対 0.5）が、90°回転によって縦に長い棒状のシルエットになって表示されていた。このゲームは上から見た視点で、生体も横長の箱として描いているため、体を90°回してもプレイヤーには「横倒しになった」ではなく「縦に伸びて棒立ちした」ように映る——上から見た視点で重力方向の「側面に倒れる」演出を持ち込んだことが逆効果だった。修正はdrawHerbivoreCarcass/drawCarnivoreCarcassからctx.rotate(Math.PI / 2)を削除し、生体と同じ水平向きのまま、脚を硬直して広げる・耳を伏せる・色を血の赤から土色へ褪せさせる、の3点だけで「倒れている」を表現するように変更（5章）。死亡直後にその場で瞬間的に死骸へ切り替わること自体（死亡tickに移動していた場合は最大1タイル分の見た目のジャンプになりうる）は今回変更していない
動物のアニメーションを「歩き」「採食/捕食」の2ループに分け、口パクを実際に食べている瞬間（rest > 0）だけ再生するように変更ユーザー報告：「草食動物がずっと口パクパクさせてて食べてるところが分からない」「肉食動物は食べるモーションが出ていない気がする」。restTicksAfterEating導入時、位置を止めれば見分けがつくはずと考えたが、実際の口パクアニメーションは経過時間だけで回る単一の8フレームループで、休憩中かどうかを一切見ておらず、草食獣は常時同じ強さで口を開閉し、肉食獣はそもそも最大開口量0.12と控えめすぎて噛む動きにすら見えなかった（コード確認で判明。設計時に見た目まで実機確認していなかった）。修正はベイク済み8フレームを歩き用(0〜4、口はほぼ閉じる)と採食/捕食用(5〜7、はっきりした一噛み)に分け、HerbivoreState.rest/CarnivoreState.rest（表示専用にHerbivoreSnapshot/CarnivoreSnapshotまで伝搬）が0より大きい個体だけ後者を再生するようにrender/sprites.tsのpickAnimalFrameを追加。肉食獣には元々存在しなかった明確な噛みポーズ（開口量0.9）を新設した。歩きループの口の動きは最小限に削り、休憩していない個体との対比を強めた
採食・捕食の直後に restTicksAfterEating（1）tickその場で休む仕組みを追加ユーザー指摘：「移動」と「採食」が毎tick同時に起きるため、歩いているだけなのか食べて止まっているのかが画面から見分けられなかった。移動=1tick・採食=1tick（噛む）+1tick（休憩）=2tickという行動ごとのコスト差をつけ、静止区間を作ることでメリハリを出した。最初の実装では休憩中も空腹度を上げ続けていたが、20 tickのトレースで検証したところ、潤沢な食料下でも空腹度が0.45〜0.5で振動するだけで繁殖しきい値(0.15)に一切近づかないことが判明した（採食の relief 0.1 と gain 0.05 が近い値に意図的にチューニングされていたため、休憩tickのgainだけが追加されると実質相殺されてしまう）。休憩中は空腹度を凍結（上げも下げもしない）する方式に変更し、以前と同じ下降トレンドを維持した（tick数では半分の速さになる）。この「潤沢に食べ続ければ繁殖しきい値に近づき続ける」性質をINV-16として regression test 化した
草食獣・肉食獣に表示専用の安定id（id）を追加し、移動補間・向き判定の個体特定を配列添字からidベースに変更ユーザー報告：「タイミングは不定だが、遠くから飛んできて重なるように見える個体がいる」。原因は前tick→今tickの補間が配列の添字だけで個体を対応づけていたこと。死亡は swap-remove（末尾の個体を空いた枠へ詰める）で実装されているため、ある個体が死んだ枠に別の生存個体が「テレポート」してくる形になり、次のtickの補間はその枠を「同じ個体が移動した」と誤認して、無関係な2個体の位置を結ぶ長距離の斜め移動を描いてしまっていた。母数が多いほど（草食獣は毎tick誰かが死にやすい）頻発するため「タイミングが分からない」という報告と一致した。修正は個体に誕生時から不変のidを持たせ（HerbivoreState/CarnivoreState、4.3/4.4章）、rendererはこのidをキーにした前tick位置のMapで補間元を引くように変更（render/renderer.ts の computeGlide）。死んだidのエントリは毎tick作り直すMapから自然に消えるので、個別の削除処理は不要。再現条件をそのまま test/renderer.test.ts の単体テストにした（死亡でid=2が別の添字に来るケースを再現し、補間元が正しくid=2自身の前回位置になることを確認）
死骸の表示を「x」の一文字グリフから、発生元の種のボディ形状を横倒しにしたベクタ図形に変更死骸が種によらず同じ記号だったため、何が倒れているか画面から分からなかった。生体のシルエット（草食獣＝丸みのある体、肉食獣＝細身＋縞模様）を再利用し、耳が垂れ脚が硬直して広がる「倒れた」ポーズにして描き分けた。色のフェード（新鮮な赤→土色）は変更していない。このためだけに CarcassState/CarcassSnapshot に species（0=草食獣・1=肉食獣）を追加した（4.5章）

11. 開発の進め方

このマニュアルをモデルとして扱う。依頼を受けたら、コードより先にこの文書の上で考える。

  1. 位置を決める：2章の因果ループで、どの箱（ストック）を足すのか、どの矢印（フロー）を足す・変えるのかを言葉にする。3章の処理順のどこに入るかも決める。
  2. 影響を洗う：7章の不変条件のどれに影響するか。4.1のピラミッドの順序を崩さないか。10章で過去に却下・決着した案の蒸し返しになっていないか。8章の未実装項目との関係。
  3. 受け入れ基準を先に書く：「何が観察できたら完成か」を、単体テストで確かめられるもの（ミクロ）と、実機で観察するもの（マクロな挙動）に分けて書く。モデルが変わるなら、実装前にマニュアルの変更案をユーザーと合意する。
  4. 実装：6章のモジュール境界を守る。数値は params.ts に置き、理由をコメントに書く。
  5. 検証：npm run typecheck、npm run test、ブラウザで観察。長時間の挙動は早送りで確認する。
  6. マニュアルを更新：同じコミットで、モデル図・処理順・パラメータ表・不変条件の状態・判断の記録を直す。確認していないものを「確認済み」にしない。
